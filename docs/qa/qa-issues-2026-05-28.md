## Issue Log

### QA-001 — P1: ReassignDropdown doesn't reflect current assignment

**Description:** On task detail for fl-006, the ReassignDropdown is initialized with
`defaultSelectedKeys={["anvil"]}` but "anvil" is not present in the agents collection fetched
from the hub. HeroUI Select fires repeated warnings: `Keys "anvil" passed to "selectedKeys"
are not present in the collection.` The dropdown appears empty/unselected instead of showing
the current agent.

**Repro:**
1. Navigate to `/workspaces/Mvxzk1PMkofoeEfiR3BPg/tasks/fl-006`
2. Observe ReassignDropdown — no agent selected, 5+ console warnings

**Suspected cause:** `GET /api/hub/agents` returns workspace-scoped agent *registrations*,
but the task's `assignedAgentId` ("anvil") is a personality ID, not a registered agent record.
The agent list and the personality-based assignment use different identifiers.
File: `src/app/(dashboard)/workspaces/[id]/tasks/[taskId]/_components/reassign-dropdown.tsx`

### QA-002 — P1: Analytics status breakdown hides 10 cancelled tasks

**Description:** The status breakdown bar and legend on the analytics overview page hardcode
`cancelled: 0` and omit the segment entirely. With 10 cancelled tasks out of 18 total (56%),
the bar represents only 8 tasks. The bar track appears mostly empty.

**Repro:**
1. Navigate to `/workspaces/[id]/analytics`, click "All time"
2. Status breakdown shows "completed 6" + "pending 2" only. No cancelled segment.

**Suspected cause:** The hub `GET /workspaces/:id/analytics/overview` endpoint does not return
a `cancelledTasks` count. The client hardcodes `cancelled: 0` with a comment `// not in
overview response; omit`. Fix requires adding `cancelledTasks` to the hub response and wiring
it into the client.
File: `packages/forge-hub/src/routes/analytics.ts:52-66` (add cancelled count to SQL)
File: `packages/forge-dash-community/src/app/.../analytics/page.tsx:94`

### QA-003 — P2: Task detail "Created by" shows raw device ID

**Description:** Task detail for fl-006 shows `Created by ni-9yuBLD33hcBGqj-wr8` — this is
the forge-master-dev device's internal ID, not its name. The source prefix (`device:`) was
stripped (fix U1 from session 5) but the ID itself is not resolved to the device name.

**Repro:**
1. Navigate to `/workspaces/[id]/tasks/fl-006`
2. Below the description: "Created by ni-9yuBLD33hcBGqj-wr8 · 5/26/2026, 7:59:20 PM"

**Suspected cause:** The task detail page strips the `device:`/`user:` prefix but doesn't do
a second lookup to resolve the bare ID to a device name. A device name lookup against the
`/devices` API would resolve "ni-9yuBLD33hcBGqj-wr8" to "forge-master-dev".
File: task detail page server component

### QA-004 — P2: Activity stream shows unresolvable raw source ID

**Description:** ~19 of 26 activity stream entries on the Workshop page show source as
`r2N2yTEsxEB2NppVtTdiY` (raw ID, no name resolution). This ID does not match any registered
device name. Events created by the forge-master device correctly show "forge-master-dev" but
older events show the raw ID.

**Repro:** Navigate to `/workspaces/[id]` — activity stream items for fl-001 through fl-004
and all older tasks show `r2N2yTEsxEB2NppVtTdiY` as source.

**Suspected cause:** These tasks were created via API with a user/session token as the source
value. The UI resolves device names by matching source against the devices list, but
`r2N2yTEsxEB2NppVtTdiY` is a user record ID, not a device ID — it won't resolve.
Fix: look up user IDs against the `/auth/me` or users API, or show "user" as a fallback label.

### QA-006 — P2: Post-logout polling fires 12x 401 errors

**Description:** After clicking "Sign out", client-side `setInterval` polls for
`/api/hub/devices` and `/api/hub/tasks?workspaceId=...` continue firing until the redirect
completes, generating 12 HTTP 401 console errors.

**Repro:**
1. Navigate to any workspace Workshop page
2. Click "Sign out"
3. During redirect: 12x `Failed to load resource: 401` in console

**Suspected cause:** The Workshop page and left-rail device polling use `setInterval` that is
not cancelled when the session is invalidated. The intervals fire several more times before the
redirect kills the page. Fix: listen for auth errors (401) in the polling handlers and
`clearInterval` + redirect on first 401.
File: workshop page and left-rail polling components

### QA-007 — P2: ReassignDropdown hydration mismatch (react-aria ID drift)

**Description:** Task detail page logs a React hydration mismatch error on every load.
Server-side renders `id="react-aria-_R_sn5esnebn5ritqkndlb_"` but client hydrates with
`id="react-aria-_R_sn5esnebn5ritqkndlbH2_"`. React cannot patch this up, causing a warning
that could affect screen-reader label associations.

**Repro:** Navigate to any task detail page with a reassignable status. Check console for
`A tree hydrated but some attributes of the server rendered HTML didn't match`.

**Suspected cause:** react-aria generates IDs using a counter that differs between SSR and
client. Known react-aria SSR issue. Fix: add `suppressHydrationWarning` to the trigger
element, or render ReassignDropdown client-only with a loading skeleton.
File: `reassign-dropdown.tsx`
